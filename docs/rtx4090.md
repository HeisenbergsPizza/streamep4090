# 单机 4 × RTX 4090：Qwen3-30B 形状的合成 decode 实验

这套脚本针对四卡都在 NUMA 0、GPU 间拓扑为 PHB、P2P read/write 均为 `NS` 的服务器。使用 BF16，Attention DP=4、Expert EP=4、TP=1；每张卡放置完整 Attention 层及每层 32 个 experts。完整配置为 48 层、128 experts、Top-k=8。

**验证状态（2026-11-01）：用户服务器已输出 `PASS: benchmark completed`，结果文件为 `reports/rtx4090/benchmark-20261101-110622.csv`。这确认本轮 benchmark 请求流程完成、吞吐及耗时为正、CSV 文件存在。benchmark 模式默认 48 层；本轮具体配置和性能数值仍待核对完整日志/CSV，PASS 打印后的 Ray 退出状态也需单独确认。**

此前服务器日志还确认硬件/import/BF16 预检及 staging、token routing、空闲线程退出共 50 项测试通过。Grouped GEMM 的 MoE down 参考精度问题及修复依据见 2.7 节。完整预检和 smoke 的最终日志尚未逐项核对；本地没有 CUDA 实机验证能力。

## 实验语义

- 本仓库使用随机初始化的权重与合成 hidden states，没有加载 Qwen checkpoint；不需要下载 Hugging Face 模型。
- 请求提供初始上下文长度和目标输出长度，驱动合成 decode 过程；初始上下文长度影响 KV 分配/attention 访问，不包含对应真实 prompt 的 prefill 计算。
- 默认路由来自随机 logits 的 Top-k，不依赖外部 routing trace，也不代表真实 Qwen 请求的专家分布。
- `server` 是仓库的 benchmark HTTP 服务，提供 `/run_once` 等实验接口，不提供 OpenAI chat/completions 接口。
- CLI 中 `--rate` 的含义是 **requests/s**：uniform 间隔为 `1/rate`，poisson 间隔均值也为 `1/rate`。
- 长度区间使用 `[min,max)`。默认 smoke 为 8 个请求、1 req/s、初始长度 64、输出长度 8；完整 benchmark 为 32 个请求、1 req/s、初始长度 64、输出长度 32。两者还会先执行仓库默认 warmup：10 个请求、5 req/s、初始长度 100、输出长度 50。

这组低负载默认值用于验证完整请求流和资源占用；测饱和吞吐时需另行扫 arrival rate，并固定层数、长度分布、路由方式、batch cap 和测量窗口。

指标中 `req_latency_*` 是首个输出 token 到最后一个输出 token 的时间，未包含请求排队和首 token 等待；ITL 是相邻输出间隔，只有一个输出 token 时没有 ITL。默认 token throughput 以收到的输出 token 数除以整段 benchmark 的提交到全部完成时间，包含 arrival 间隔和 drain；日志中的瞬时吞吐使用另一时间窗口。`--analyze-throughput` 会改用仓库的窗口分析，比较时应明确是否启用。

### 2.7 修复 Grouped GEMM 测试参考的精度设置

服务器上的 `test_moe_pattern` 曾在比较 `cache_down` 与 BF16 `ref_down` 时失败。诊断使用相同的输入和权重，得到以下结果（阈值均为 `atol=0.1, rtol=0.1`；FP64 参考计算后舍入到 BF16）：

| 比较 | 超差元素数 / 65536 | RMS 误差 |
| --- | ---: | ---: |
| CUTLASS vs 原 torch 参考 | 601 | 10.649905 |
| CUTLASS vs FP64 舍入参考 | 0 | 0.26184229 |
| 原 torch 参考 vs FP64 舍入参考 | 605 | 10.652614 |
| CUTLASS vs 关闭 BF16 低精度归约的 torch 参考 | 0 | 0.25429812 |
| 关闭 BF16 低精度归约的 torch 参考 vs FP64 舍入参考 | 0 | 0.062675231 |

这些结果将本次失败定位到原 torch 参考的精度设置。CUTLASS 使用 FP32 累加；PyTorch 的 BF16 GEMM 默认允许较低精度的中间归约，参见 [PyTorch 2.6 数值精度说明](https://github.com/pytorch/pytorch/blob/v2.6.0/docs/source/notes/numerical_accuracy.rst#reduced-precision-reduction-for-fp16-and-bf16-gemms)。超差数为 0 表示满足现有容差，仍存在非零误差。

当前 `tests/ops/test_grouped_gemm.py` 在 `_ref_grouped_gemm` 中默认关闭 `allow_bf16_reduced_precision_reduction`，计算后恢复原设置，直接执行和测试函数调用均生效。输入/输出仍为 BF16，所有通过阈值保持不变；失败时保留误差统计、FP64 参考和显式开启低精度归约的对照。更新服务器同名文件后执行 `bash experiments/scripts/rtx4090/preflight.sh`，无需重新编译扩展。

也可在 StreamInfer 目录中先单独运行 Grouped GEMM 的全部 eager/Graph 测试，日志保存在 `reports/rtx4090/`：

```bash
(
  set -euo pipefail
  export PYTHON="$CONDA_PREFIX/bin/python"
  source experiments/scripts/rtx4090/common.sh
  rtx4090_env
  rtx4090_libraries
  mkdir -p reports/rtx4090
  "$PYTHON" tests/ops/test_grouped_gemm.py --seed 0 \
    2>&1 | tee reports/rtx4090/grouped-gemm-full-reduction.log
)
```

启动日志中的 `reference ...=False (scoped)` 表示参考计算已禁用低精度归约，随后显示的 `process setting=True` 可以是恢复后的正常全局默认值。旧选项 `--no-bf16-reduced-precision` 继续支持，但新版参考函数已不依赖该选项。修改仅涉及测试参考，不改变 CUTLASS 推理内核。完整预检仍须通过后再运行 smoke。测试输出中的 `The CUDA Graph is empty` 警告若来自 `test_gather_ops_reject_raw_host_tables_during_cuda_graph_capture`，是该测试刻意拒绝捕获 host 指针操作后留下空 graph；应与后续 GEMM 断言分别看待。

## 3. 实机预检

四张 GPU 应空闲，初始检查要求每卡至少 20 GiB free、至少 16 个可用逻辑 CPU、`/dev/shm` 至少 1 GiB free。容器可使用 `--gpus all --shm-size=2g` 或更大的共享内存；64 MiB 的默认容器 `/dev/shm` 不满足此配置。

```bash
bash experiments/scripts/rtx4090/preflight.sh
```

预检包含：

- `nvidia-smi` 与 GPU topology 输出。
- 恰好四张 RTX 4090 / sm89、显存、CPU、共享内存检查。
- torch、vLLM/CUDA extension、Triton、Ray、StreamInfer 核心模块 import；vLLM patch 签名检查。
- 每卡 BF16 matmul 数值检查，扩展未链接 GDRCopy/NIXL 的检查。
- 无 GDRCopy staging、token permutation/加权返回/Top-k sum 的新 CUDA 数值测试，以及现有 CUTLASS grouped GEMM 数值/graph 测试。
- 单 GPU 上真实 native 空闲通信线程退出测试（子进程有 30 秒 timeout）。
- 四进程、六对 GPU、独立 2-rank NCCL groups 的双向 BF16 send/recv 数值检查，payload 为 1、4096、1048576 个 BF16 元素。

硬件/import 检查 timeout 为 120 秒；每组 CUDA 数值测试和 NCCL 检查为 180 秒（NCCL 单 group timeout 45 秒），超时后非零退出。结果保存至 `reports/rtx4090/preflight-*.log`。该 NCCL 测试使用 PyTorch NCCL API；StreamInfer 自己的 communicator/dispatcher/pool 还要由后续 smoke 覆盖。

针对已知无 P2P 拓扑，所有运行脚本固定：

```text
NCCL_P2P_DISABLE=1
NCCL_IB_DISABLE=1
NCCL_SHM_DISABLE=0
NCCL_CUMEM_HOST_ENABLE=0
```

保留 NCCL 的主机共享内存路径。检查 `NCCL_DEBUG=INFO` 日志确认目标服务器实际选用的传输；以上开关不代表已测得带宽或延迟。空闲时 PCIe current gen 降到 1 不等同于满载性能，负载下应另行观察。

`NCCL_CUMEM_HOST_ENABLE` 从 NCCL 2.23 才存在；设为 0 可在使用更新 NCCL 时保留传统 host allocation。标准 torch 2.6 wheel 的较早 NCCL 不依赖该开关，实际版本由预检打印。参见 [NVIDIA 环境变量说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html#nccl-cumem-host-enable)。

## 6. 后续调参和故障定位

CPU/GPU 时间线采集见 [四卡 profiling 操作说明](rtx4090-profiling.md)，包含 Nsight CLI 安装、扩展重编、baseline/trace 对照和报告查看。

- **先比较完整深度的无 graph 基线**。确认正确完成后，单独开启 graph 做小批次试验：

  ```bash
  bash experiments/scripts/rtx4090/launch.sh smoke \
    --cuda-graph-attn --cuda-graph-expert --max-attn-graph-bsz 16
  ```

  Graph 会增加常驻 buffer/捕获内存；sm89 fallback 与 graph 的组合也需要目标 GPU 验证。全深度开启前重新检查显存。
- **OOM**：先确认其他 GPU 进程，再降低 batch cap。若总内存分配或运行临时峰值超限，可降低 KV 目标比例 `--gpu-usage`；若错误明确是预算扣除权重后无剩余 KV 空间，继续降低该比例会更坏，需要核查 profile/占用并在实测余量内调整。保留完整错误日志。减少层数可定位启动路径，但性能数值要标明层数。
- **NCCL hang/timeout**：保留 preflight log、`NCCL_DEBUG=INFO` 日志和 `nvidia-smi topo -m`。先核查容器 `/dev/shm`、进程退出与端口占用；不要通过关闭 SHM 或改动 driver/ACS 绕过问题。
- **CUDA/ABI/import 错误**：检查当前 Python 环境、torch 2.6.0 / vLLM 0.8.2、patch 状态、`CUDA_HOME`、NCCL 库路径；在当前服务器重新编译。
- **外层 timeout=124**：表示整个实验未在时限内正常结束，不能当作完成。保留 `/tmp/streamep-ray-*` 和 `reports/rtx4090/` 供排查；若 Python 卡在 native call，最后的强制终止可能留下本次 Ray 子进程，请按日志中该次 session/PID 清理。

### 6.1 启动前提示 24000 端口不可用

24000 是 GPU 0 的 ZMQ 元数据端口，其他三卡为 24016、24032、24048。这组端口由 C++ 常量计算，修改 `MASTER_PORT` 不会改变它们。检查发生在本次 Ray cluster 创建之前。

先在服务器执行只读检查：

```bash
ss -ltnp 'sport = :24000'
ss -tanop 'sport = :24000'
```

`ss` 不存在时安装 `iproute2`；若缺少进程信息，可用 `sudo ss` 重查。`-l` 查看监听者，`-a` 查看全部 TCP 状态，`-p` 显示可见的进程信息，`-o` 显示计时器，参见 [ss 手册](https://man7.org/linux/man-pages/man8/ss.8.html)。

- **有 LISTEN/PID**：核对进程命令、所属用户及本次实验的 Ray session。若确实是自己的上一轮运行，优先在其终端用 Ctrl-C 正常退出；残留进程按确认的 PID 处理。不要批量停止机器上的 Ray/Python 进程。
- **只有 TIME_WAIT、没有监听者**：旧连接已经关闭，无需终止进程。可以等状态消失后重试。旧版预检未设置 `SO_REUSEADDR`，会误拦实际 ZMQ 可以复用的地址。
- **没有对应 socket 或错误涉及权限**：保留完整异常链；容器中进程可见性、检查时机等也可能影响观察，不要据此猜测需要结束哪个进程。

当前 `run_local.py` 对 ZMQ 端口采用与 [libzmq TCP listener](https://github.com/zeromq/libzmq/blob/v4.3.4/src/tcp_listener.cpp) 一致的 `SO_REUSEADDR`，执行 `bind + listen` 后立即释放；不设置 `SO_REUSEPORT`，真实监听冲突仍会被拒绝。其他系统错误会保留原始 errno/消息。更新服务器的 `experiments/scripts/rtx4090/run_local.py` 即可，无需重新编译；这项修改不能清理已有进程或保证检查后端口一直空闲。

用户随后报告：服务器未更新上述端口检查代码，安装 `iproute2` 后重试即完成 benchmark。因此该次恢复不能归因于本地代码修改；两次运行之间可能发生了旧连接状态过期或旧进程退出。未取得故障当时的 socket 状态，尚不能确定具体原因。
